# Supporting documents and case collections

Use this guidance for galleries, annotated examples, and reference collections that readers skim, compare, or consult alongside a main guide. Their purpose is to help readers recognize the lesson in each example.

Briefly explain what the collection covers and link to the main guide for broader concepts. Give each entry enough local context to connect the evidence with its interpretation. State assumed knowledge when it matters, rather than repeating the main guide's explanations in every case.

Choose shared fields that make the cases easy to compare, and preserve the user's requested structure. **Issue → Change → Lesson → Outcome** is one useful example. Keep field meanings consistent: distinguish observed changes from proposed fixes, and state when an outcome is missing. Vary the detail within each field according to what the evidence can explain.

Keep descriptions brief without turning them into shorthand. Put routine asset details and acquisition notes in a provenance reference when one exists, while keeping source links and important limitations beside the claims they support.

For example, a **fictional case about a reading app** could use:

- **Issue:** A reviewer asked which features the subscription includes. The original screen promised better reading without naming the paid tools.
- **Change:** The developer added book import and text analysis to the list of paid benefits.
- **Lesson:** Name the features customers get when they pay so they can decide whether the subscription meets their needs.
- **Outcome:** The developer reported approval after changing both the screen and the store listing. This example cannot show which change led to approval.

The shared fields let readers find the same information across cases; the sentences explain the actor, action, and consequence. Use a different structure when it better serves the collection's question.
